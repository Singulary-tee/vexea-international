# Live Service Security and Authority Planning

This document lists identified issues, structural bypasses, and security vulnerabilities across the VEXEA codebase where client-side trust or state bypasses the authoritative model of the live service, alongside their corresponding architectural solutions aligned with the live service paradigm.

---

## 1. User Inventory & Class Loadout Management

### Code Evidence
In `/client/src/systems/ClassLoadoutPersistence.ts`:
```typescript
export class ClassLoadoutPersistence {
  private static readonly STORAGE_KEY = "vex_class_loadouts";
  // ...
  public static getClassLoadout(classId: string): LoadoutSlotItem[] {
    try {
      const raw = localStorage.getItem(STORAGE_KEY);
      // ...
    }
  }
}
```

### Analysis of Concept Defiance
The current module relies on local storage to preserve, retrieve, and potentially edit equipment loadouts under the assumption of "offline" persistence. In a live service multiplayer FPS, trusting client-side local storage or allowing arbitrary loadout updates to propagate directly to the matchmaker bypasses inventory verification. Players could equip unearned, locked, or modified weapons.

### Recommended Architectural Solution (Firestore-centric with Client Cache & Optimistic Updates)
1. **Durable Firestore Inventory**: The source of truth for all unlocked weapons and attachments resides in the user's Firestore document (under the `unlockedItems` array field).
2. **Optimistic Client Updates**:
   - The client loads the user profile once from Firestore and caches it locally in memory.
   - For simple operations (e.g., viewing weapons, swapping compatible slots), the client performs instant optimistic updates on the UI.
   - Swaps are validated locally against the cached inventory profile to ensure the player can only equip what they genuinely own, preventing repeated, expensive database queries for simple layout clicks.
3. **Inventory Sanitation at Match Entry**:
   - When the client requests matchmaking or connects to a match room, the server fetches the official Firestore document for the player.
   - The server cross-references the equipped class loadout with the authoritative `unlockedItems` array.
   - Any invalid or unowned equipment is automatically sanitized and reverted to the default weapon configuration before the player character is spawned.

## 2. Economy and Cosmetic Purchase Verification

### Code Evidence
In `/client/screens/store-screen.ts`:
```typescript
async function handleStorePurchase(price: number, itemId: string, itemTitle: string, userData: any, container: HTMLElement): Promise<void> {
  const currentCredits = userData?.credits !== undefined ? userData.credits : 1000;
  if (currentCredits < price) {
    alert(`INSUFFICIENT CREDITS.`);
    return;
  }
  // Client calculates credit changes and writes directly to Firestore...
  const newCredits = currentCredits - price;
  await updateDoc(doc(db, 'Users', auth.currentUser.uid), {
    credits: newCredits,
    unlockedItems: arrayUnion(itemId)
  });
}
```

### Analysis of Concept Defiance
The client directly handles balance calculations (`currentCredits - price`) and executes direct updates to the database. Due to permissive Firestore rules, a compromised client can inject arbitrary values into their user document, bypassing price validation and manually adding item IDs or granting themselves infinite credits.

### Recommended Architectural Solution (VerificationService Integration)
1. **VerificationService Execution**:
   - All purchases must be sent through the `VerificationService.processPurchase(input, item)` API.
   - The `VerificationService` consumes a secure `VerifyPurchaseInput` interface and audits the purchase against strict level, ownership, and credit requirements using pure, worker-ready rules.
2. **Secure Firestore Rules Integration**:
   - Restrict Firestore security write rules for `/Users/{playerId}` to prevent direct field writes for `credits` and `unlockedItems`.
   - Implement transactions where writes are only approved if the new state matches the validated outcome generated by the service (using Firestore security rules checking that increment operations or credit deductions match the item catalog pricing).
   - This ensures the game server is never bogged down with store transactions, leaving the dedicated databases and serverless endpoints to handle purchase auditing.

## 3. Social Graph & Friends System

### Code Evidence
In `/client/social.ts`:
```typescript
export async function sendFriendRequest(myUid: string, targetUid: string) {
  // Decentralized client-side batches writing to separate collections
  const batch = writeBatch(db);
  const myFriendRef = doc(db, "Users", myUid, "friends", targetUid);
  // ...
  const incomingRef = doc(db, "incomingRequests", targetUid, "requests", myUid);
  // ...
  await batch.commit();
}
```

### Analysis of Concept Defiance
Handling multi-step friendship queries and synchronization through client-driven batches creates desynchronized state and introduces latency overhead. When clients go offline or disconnect during a multi-write transaction, the social graph fractures, leaving asymmetric relationships (e.g., Player A sees Player B as accepted, but Player B still sees a pending request).

### Recommended Architectural Solution (Firebase Realtime & Firestore Native Social Graph)
1. **Reactive Database Subscriptions**:
   - Social updates, player status notifications, and real-time status updates (e.g., Online, In-Match) must be managed using native Firestore and Firebase Realtime Database triggers.
   - By leveraging listener subscriptions (`onSnapshot`), clients instantly synchronize status without manual REST polling or complex custom server routing.
2. **Consolidated Social Schema**:
   - Restructure friendship states to reside in self-contained subcollections under `Users/{userId}/friends` with bidirectional rules.
   - Use atomic Firebase writes or serverless functions to update friendship states symmetrically in one step, protecting the primary game matchmaking and simulation servers from handling social routing overhead.

## 4. Server-Authoritative Physics & Hitscan Origin Verification

### Code Evidence
In `/server/index.ts`:
```typescript
const dirX = args.direction.x;
const dirY = args.direction.y;
const dirZ = args.direction.z;
const timestamp = args.timestamp;

const expectedT = Date.now() - pState.ping;
let targetTick = currentRoom.serverTick;
if (Math.abs(timestamp - expectedT) <= 50) {
  const rewindMs = Math.min(200, Date.now() - timestamp);
  targetTick = currentRoom.serverTick - Math.floor(rewindMs / 16.66);
}
```

### Analysis of Concept Defiance
While the server validates hitscan collision targets historically using historical bounding box (AABB) records to support lag compensation, it accepts the shot `origin` vector from the client's payload (`args.origin`) without validating that the coordinate matches where the player's physical avatar was actually located at that specific point in time in the physics simulation.

### Recommended Architectural Solution (Authoritative Origin Auditing)
1. **Historical Position Retrieval**:
   - For every hitscan verification request, look up the player's recorded physics position at the reconstructed `targetTick`.
2. **Vector Deviation Sanity Check**:
   - Compare the client-reported `args.origin` with the authoritative simulated position of the player's body in the physics engine.
   - Set a maximum allowed spatial deviation threshold (e.g., up to 1.5 meters to account for variable weapon offsets, crouching states, and minor network jitter).
3. **Deterministic Shot Rejection**:
   - Reject any incoming hitscan event where the shot origin is further than the safe deviation threshold, preventing wall-clipping bypasses and floating client-teleportation fire exploits.
