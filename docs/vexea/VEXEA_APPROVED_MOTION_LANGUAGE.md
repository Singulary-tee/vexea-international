# VEXEA Approved Motion Language

## Surviving reference

The approved matchmaking direction is not a generic spinner or a minimal circle. It is a restrained radial field with a dominant primary ring, a dense but deliberately gapped tick band, faint inner construction, a large low-opacity outer boundary, and discoverable axes/diagonals. The hierarchy is legible before the viewer notices every detail.

Its important quality is not the number of primitives. It is the **composition and timing**: the field fades in, rings expand, the primary ring traces, inner details sustain quietly, and the found state resolves with a shorter, stronger terminal arc. The user can look at the center phrase and understand the state, then discover the supporting geometry around it. Nothing explains the motion with a SaaS-style dashboard.

## Rules for the next candidates

Loading and battle pass must borrow this behavior-level grammar rather than copy the radial geometry. Each needs one dominant visual event, a supporting layer that rewards closer attention, and a clean terminal state. The animation must be readable from the overall silhouette and timing before metadata is read.

The next loading candidate must therefore avoid progress-widget chrome. It should present a single game-relevant visual event that can sustain a long wait: a clear entrance, one or two subordinate internal changes, and a decisive resolution. Percentage/state text may exist, but it cannot be the composition.

The next battle-pass candidate must make progression legible through a single visual subject and an authored state change. It must not become a rail, ledger, grid, or arrangement of equal cards. The current reward/progression state should be understood from the composition, with the motion reserved for the moment of advancement or claim.

## Rejection triggers

Reject any candidate where the first read is a line, box, row, card, or equal-weight collection of shapes. Reject explanatory labels that carry the visual idea instead of the animation. Reject decorative complexity without a dominant silhouette. Reject repeated looping motion that has no state purpose. Reject anything that looks like a component library demo rather than an internal game surface.

## V5 inspection checkpoint

The v5 facility-wake loading field was rendered and inspected at 390px and desktop scale. It uses the approved matchmaking grammar directly: a dominant outer/primary arc hierarchy, faint inner construction, a separated tick band, and a meaningful central VEXEA eye mark. The field is the visual event; metadata is subordinate.

The v5 season-crest candidate was also rendered and inspected at both sizes. It uses one large central tier seal, one release arc, one reward mark, and sparse position labels. It does not contain a rail, ledger, card grid, or travelling object. Both candidates remain visual approval work only.

The v6 candidates were rendered at 390px and desktop width and inspected after the loading sweep overflow was found and corrected. The post-fix live DOM test reports both stages settled with `run: false`, `settled: true`, and `overflow: false`. The final phone capture keeps the controls separate from the stages and preserves the single central event for each candidate.
